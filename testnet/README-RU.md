# Тестовая сеть Latheon на сервере

Комплект поднимает на одном сервере:
- узел L3 (Arbitrum Nitro) поверх Arbitrum Sepolia, газ в тестовом LTH;
- публичный RPC по HTTPS: `https://RPC_HOST`;
- обозреватель блоков Blockscout по HTTPS: `https://EXPLORER_HOST`.

Это тестовая сеть. Тестовый LTH к реальному токену отношения не имеет.

Вся процедура отрепетирована в GitHub Actions (workflow `testnet server stack (rehearsal)`): тот же `setup-server.sh`, тот же `deploy-chain.sh`, те же контейнеры. Отличия CI от сервера: самоподписанный сертификат вместо Let's Encrypt, без ожидания финальности и пакеты каждые 30 секунд.

## Что нужно заранее

1. Сервер: Ubuntu 24.04, 8 ядер, 16 ГБ памяти, от 150 ГБ диска, SSH-ключ.
2. Отдельный кошелёк деплоя примерно с 0,1 ETH в Arbitrum Sepolia (0,02 уйдёт адресу, который публикует пакеты, 0,01 — валидатору).
3. RPC Arbitrum Sepolia, который отдаёт `eth_getLogs` по широкому диапазону блоков: узел читает inbox и утверждения кусками до тысяч блоков. Бесплатный Alchemy (10 блоков) и бесплатный QuickNode (5) не подходят: узел бесконечно повторяет запросы и не видит депозитов. Кроме того, RPC должен отдавать состояние на блоке `finalized`: валидатор BoLD при старте читает там rollup, иначе узел падает с `historical state … is not available` (так ведёт себя publicnode). Без ключа подходит `https://sepolia-rollup.arbitrum.io/rpc` (проверено 20.10.2026). Проверка кандидата (обе команды должны вернуть `"result"`):
   ```bash
   curl -s -X POST -H 'content-type: application/json' --data '{"jsonrpc":"2.0","id":1,"method":"eth_getLogs","params":[{"fromBlock":"0x131ea6ef","toBlock":"0x131eaad7","address":"0x4D1FdE71BAd635148727694FEa04f24CAf881990"}]}' АДРЕС_RPC | head -c 200
   curl -s -X POST -H 'content-type: application/json' --data '{"jsonrpc":"2.0","id":1,"method":"eth_call","params":[{"to":"0xdDcA9a000d2DE69D6C11050B9e8fe90B5e02Bd89","data":"0x45e38b64"},"finalized"]}' АДРЕС_RPC
   ```
   Подходит, если в ответе `"result":[`, а не `error`.
4. Две DNS-записи типа A на IP сервера, например `rpc.testnet.latheon.xyz` и `explorer.testnet.latheon.xyz`. Их добавляют там, где управляется DNS домена latheon.xyz.

## Шаги

С ноутбука (PowerShell), подставив IP сервера:

```powershell
ssh -i "C:\Users\smirn\.ssh\latheon_server" root@IP_СЕРВЕРА
```

Дальше всё на сервере:

```bash
git clone https://github.com/latheon-network/l2-eval-ci.git
cd l2-eval-ci/testnet
./setup-server.sh
nano .env          # RPC_HOST, EXPLORER_HOST, PARENT_RPC
./deploy-chain.sh  # спросит ключ кошелька деплоя, ввод скрыт
```

`deploy-chain.sh`:
1. разворачивает в Arbitrum Sepolia тестовый LTH, контракт курса газового токена и контракты сети;
2. пишет конфигурацию узла и запускает все контейнеры;
3. ждёт, пока узел начнёт отвечать. Первый раз узел ждёт финальности блока с созданием сети, это до часа;
4. заводит 10 000 тестовых LTH в сеть на адрес деплоя, создаёт мост для других токенов, проверяет публикацию пакетов.

Скрипт можно перезапускать: готовые шаги пропускаются.

## Что хранить и чего не публиковать

- `chain/secret/` содержит ключи адреса публикации пакетов и валидатора и конфигурацию узла. Сделай резервную копию на ноутбук и никуда не выкладывай:
  ```powershell
  scp -i "C:\Users\smirn\.ssh\latheon_server" -r root@IP_СЕРВЕРА:/root/l2-eval-ci/testnet/chain/secret "C:\Users\smirn\Desktop\Latheon Network\testnet-secret-backup"
  ```
- `.env` содержит пароль базы и адрес RPC с ключом. Не публиковать.
- `chain/out/chain.json` хранит только публичные данные: адреса контрактов, chainId, хеши транзакций.

## Контракты Latheon в сети (неделя 2)

После `./deploy-chain.sh`, когда RPC сети отвечает и на кошельке деплоера есть LTH в самой сети (его туда кладёт шаг `fund`):

```bash
cd ~/l2-eval-ci/testnet
./latheon-cmd.sh deploy     # спросит ключ деплоера, ввод не отображается
./latheon-cmd.sh smoke      # проверка с настоящими доказательствами
```

`deploy` разворачивает Poseidon, верификаторы вывода и раскрытия, четыре нативных пула V5 (100 / 50 / 10 / 1 LTH) и нативный роутер. Потом проверяет каждую связь: признак нативной монеты, верификатор и номинал каждого пула, `zeros(8)` (ошибочную привязку Poseidon), пулы и лимиты роутера, и по одному настоящему доказательству на оба верификатора. Повторный запуск ничего не разворачивает заново, а берёт уже развёрнутое.

`smoke` вносит 11 LTH через роутер одной транзакцией двумя нотами (10 и 1), выводит обе одним `withdrawMany` с настоящими доказательствами на новый пустой адрес и проверяет, что на нём ровно 11 LTH, у роутера ничего не осталось, а в каждом пуле лежит номинал × (депозиты − выводы). В конце проверяет доказательство раскрытия. Ключ тестового получателя остаётся в `latheon/secret/`.

Почему нативные пулы: в нашей сети LTH — родная монета, ею платят газ. Пулы и роутер принимают LTH прямо в транзакции и выплачивают его напрямую (`contracts/LatheonShieldedPoolV5Native.sol` и `contracts/LatheonDistributionPoolNative.sol` в репозитории Latheon): без обёртки и без approve. Схема, верификатор, дерево и привязка к получателю те же, что у V5. Получатель с пустым адресом сразу получает LTH и может им платить газ. Сравнение газа с вариантом на обёртке: `latheon/bench/` (локальная сеть).

Результат для демо: `latheon/out/latheon-deployments.json` (запись в формате `demo/deployments.json`). Файлы схем скачиваются по коммиту Latheon и сверяются по хешам; тестовые ноты остаются в `latheon/secret/`.

## Валидатор и выводы обратно в Arbitrum Sepolia

Валидатор работает в том же узле (роль staker, стратегия MakeNodes, протокол BoLD). Он заново исполняет блоки сети, публикует в Arbitrum Sepolia утверждения о её состоянии и подтверждает их по истечении периода оспаривания. Только после подтверждения вывод из сети можно исполнить в Arbitrum Sepolia. Ключ валидатора создаётся при `deploy` и лежит в `chain/secret/`; на газ он получает 0,01 ETH, залог 0,0001 ETH узел сам оборачивает в WETH.

Сроки на сервере (параметры тестовой сети по умолчанию): утверждения не чаще раза в 15 минут, период оспаривания 30 минут, и валидатор читает только финализированные блоки Arbitrum Sepolia. Вывод становится исполнимым примерно через час после отправки. В CI те же шаги идут за несколько минут: период оспаривания 10 блоков и чтение последних, а не финализированных блоков (`BOLD_FAST`, `CONFIRM_PERIOD_BLOCKS`, `MIN_ASSERTION_PERIOD_BLOCKS` в `.env`; два последних действуют только при создании сети).

```bash
./chain-cmd.sh validator   # баланс валидатора, разрешён ли он сетью, последнее подтверждённое утверждение
./chain-cmd.sh withdraw    # выводит 10 LTH из сети на адрес деплоя в Arbitrum Sepolia и ждёт подтверждения (до 150 мин)
```

`withdraw` можно прервать и запустить снова: он продолжит ждать тот же вывод. Адресу валидатора нужен ETH в Arbitrum Sepolia, как и адресу публикации пакетов: адрес в `chain/out/chain.json` (`validator`).

## Кран тестового LTH (faucet)

Страница: `https://EXPLORER_HOST/faucet` (отдельная DNS-запись не нужна). Сервис `faucet` запускается вместе с остальными контейнерами; пока у него нет ключа, страница пишет «not configured».

```bash
cd ~/l2-eval-ci/testnet
./faucet-cmd.sh init          # создаёт отдельный ключ крана в faucet/secret/faucet.key и показывает адрес
./faucet-cmd.sh fund 5000     # переводит 5000 LTH с кошелька деплоя на кран (спросит ключ, ввод скрыт)
./faucet-cmd.sh address       # адрес и баланс крана
```

Правила (меняются в `.env`: `FAUCET_AMOUNT`, `FAUCET_COOLDOWN_HOURS`, `FAUCET_DAILY_CAP`):
- 100 LTH за раз; не чаще раза в 24 часа на адрес и на IP;
- не больше 5000 LTH за сутки всего;
- адресу, у которого уже есть 100 LTH или больше, не выдаёт;
- запросы отправляются по одному, записи о выдачах хранятся в `faucet/secret/claims.json` и переживают перезапуск.

У крана свой кошелёк: если его ключ утечёт, под угрозой только баланс крана. `faucet/secret/` не публиковать; в резервную копию добавить вместе с `chain/secret/`. Капчи нет: от массового сбора защищают только лимиты, это тестовая монета.

Зачем кран при нативных пулах: первой транзакции нового адреса (депозит) нужен LTH на газ и на сам депозит. Вывод на пустой адрес приносит ему LTH, так что газ для дальнейших действий у получателя уже есть.

## Обслуживание

Сводка одной командой, ключ не нужен и не выводится:

```bash
cd ~/l2-eval-ci/testnet
./status.sh        # контейнеры, ошибки узла за час, диск; блоки, пакеты, валидатор, кому идут комиссии,
                   # ETH batch poster, валидатора и деплоера в Arbitrum Sepolia, где лежит тестовый LTH, предупреждения
./status.sh 24     # то же, ошибки узла за сутки
```

Завести в сеть больше тестового LTH (депозит идёт 20–60 минут, через финальность Arbitrum Sepolia; спросит ключ):

```bash
L3_DEPOSIT=50000000 ./chain-cmd.sh fund
```

Остальное:

```bash
docker compose ps                 # состояние
docker compose logs -f --tail 50 nitro
./chain-cmd.sh batches            # пакеты доходят до Arbitrum Sepolia?
docker compose restart nitro
```

Адресу публикации пакетов нужен ETH в Arbitrum Sepolia. Адрес лежит в `chain/out/chain.json` (`batchPoster`), баланс видно на sepolia.arbiscan.io. Пополнять, когда остаётся меньше 0,005 ETH.

## Чего пока нет

- Один валидатор, и это наш же узел: оспорить его утверждения некому. Для тестовой сети этого достаточно, но доверие к выводам держится на нём.
- Blockscout: последняя публичная версия образов 9.0.2 (бэкенд) и v2.3.1 (интерфейс). Внутренние транзакции не отслеживаются, потому что отладочные методы узла закрыты снаружи.
- Ограничение частоты запросов на один IP: публичный RPC 25 в секунду и 600 в минуту, API обозревателя 40 в секунду и 1200 в минуту (сверх этого ответ 429 с Retry-After); страницы обозревателя не ограничены. Значения меняются в `.env` (`RPC_RATE_PER_SECOND` и др.), после изменения `docker compose up -d caddy`. Caddy собирается с модулем rate_limit из `caddy/Dockerfile` (`docker compose build caddy`, несколько минут), проверка в CI: workflow `caddy with rate limits`. Тело запроса ограничено 1 МБ, пакетный JSON-RPC запрос считается за один.
- Контракты Latheon разворачиваются командой `./latheon-cmd.sh deploy` (см. выше); в демо сеть ещё не подключена: нужна поддержка нативных пулов (депозит с `value`, без approve).

## Пополнить отправителя пакетов или валидатора ETH

Если MetaMask не отправляет, это можно сделать с сервера: `./topup-cmd.sh batch-poster 0.1` или `./topup-cmd.sh validator 0.05` (сумма в ETH, не больше 1). Ключ деплоера спрашивается скрыто и нигде не сохраняется. Скрипт показывает балансы до и после и ссылку на транзакцию в Arbiscan.

## Оформление обозревателя

Логотип, иконка и картинка для соцсетей лежат в `brand/` (logo-light.png и logo-dark.png высотой 48 px, icon.png и icon-light.png 180×180, og.png 1200×600). Caddy отдаёт их по `https://EXPLORER_HOST/brand/…`. После правки: `docker compose up -d caddy frontend`; favicon собирается при старте контейнера frontend.

## Наблюдение снаружи

Workflow `testnet monitor` в этом репозитории каждые 15 минут проверяет публичный RPC, API и страницы обозревателя, страницу и баланс крана, ETH у batch poster и валидатора в Arbitrum Sepolia (адреса и пороги: `monitor/targets.env`). При проблеме запуск падает, а если в репозитории заданы секреты `TG_BOT_TOKEN` и `TG_CHAT_ID`, приходит сообщение в Telegram на русском: когда проблема появилась или изменилась, напоминание раз в 2 часа, пока она есть, и одно сообщение, когда всё снова работает. Ручной запуск с галочкой присылает текущую сводку. Плановые запуски GitHub может задерживать, это не замена наблюдению на самом сервере (`./status.sh`).

## Бот в Telegram и панель на планшете

**Бот** (сервис `bot`) отвечает только в чат `TG_CHAT_ID`:
- `/status` — сводка: блок сети, публичный RPC и обозреватель, пакеты и утверждение в Arbitrum Sepolia, ETH у batch poster, валидатора и деплоера, кран, пулы, предупреждения;
- `/menu` — кнопки: сводка, перезапуск сервиса, логи сервиса (последние 25 строк), кран (пауза, возобновление, пополнение на 10 000 или 50 000 LTH), ссылка на панель. Каждое действие, кроме сводки и логов, требует второго нажатия «Да», подтверждение действует 5 минут, одновременно выполняется одно действие.

У бота нет ни доступа к Docker, ни ключей сети. Он кладёт запрос в `ops-queue/`, а `ops-runner.sh` на самом сервере (запускается systemd) выполняет его по фиксированному списку: перезапуск и логи сервисов `nitro blockscout frontend faucet caddy db bot`, пауза и возобновление крана, пополнение крана. Всё остальное отклоняется. Журнал действий: `ops-queue/actions.log`.

Кран пополняется с отдельного **кошелька пополнений** (ключ `faucet/secret/ops.key`), а не с деплоера. В нём держим ограниченную сумму, за раз бот переводит не больше 50 000 LTH.

**Панель**: `https://EXPLORER_HOST/ops/` — страница только с публичными данными (те же, что в сводке, плюс графики за 7 дней). Данные пишет бот: снимок каждые 2 минуты, точка истории раз в 15 минут. На Android: открыть в Chrome → меню ⋮ → «Добавить на главный экран» (или «Установить приложение»).

Включить (один раз, на сервере):

```bash
cd ~/l2-eval-ci && git pull && cd testnet
nano .env                       # TG_BOT_TOKEN и TG_CHAT_ID — те же, что в секретах GitHub
./ops-install.sh                # исполнитель запросов бота (systemd)
./faucet-cmd.sh ops-init        # кошелёк пополнений, показывает адрес
./faucet-cmd.sh fund-ops 200000 # перевести на него LTH с деплоера (спросит ключ)
docker compose up -d bot faucet caddy
```

Проверка: боту `/menu` → «Кран» → «Кошелёк пополнений» покажет адрес и баланс. Панель: `https://EXPLORER_HOST/ops/`. Журнал бота: `docker compose logs --tail 20 bot`.

## Пулы V6: вместимость 1 048 576 депозитов, комиссия релейера в доказательстве

Пулы V5 рассчитаны на 256 депозитов каждый (дерево из 8 уровней) и помнят 30 последних корней. Для открытого теста этого мало, поэтому рядом ставится набор V6:

- дерево из 20 уровней: 1 048 576 депозитов на пул;
- 100 последних корней (доказательство, сделанное по старому корню, остаётся годным, пока после него не прошло 100 депозитов в этот пул);
- схема `withdraw_v4`: в доказательство вшиты получатель, адрес релейера и комиссия, отправитель транзакции не может поменять ни одно из трёх.

```bash
cd ~/l2-eval-ci && git pull && cd testnet
./latheon-cmd.sh deploy-v6    # верификатор V4, четыре пула V6, роутер V6; ключ деплоера скрыто
./latheon-cmd.sh smoke-v6     # депозит 11 LTH, withdrawMany с комиссией, депозит 23 нотами для замера газа
docker compose up -d relayer bot faucet
```

V5 остаётся: ноты, внесённые туда, выводятся как раньше. Демо показывает V6 первыми.

Ограничения V6, о которых надо знать:
- ключи схемы `withdraw_v4` — разработческие, сделаны одним человеком (`docs/dev-ceremony-v4.md` в репозитории Latheon); для настоящих денег нужна публичная церемония;
- депозит одной ноты дороже по газу, чем в V5 (глубже дерево); `smoke-v6` печатает измеренные значения;
- `smoke-v6` вносит 999 LTH нотами со случайными обязательствами, которые никто не может вывести: эти LTH навсегда остаются в пулах и завышают их баланс;
- роутер принимает до 32 нот за депозит и до 16 за `withdrawMany`.

## Лимиты крана и релейера, исключения по IP

В `.env` (после изменения `docker compose up -d faucet relayer`):
- кран: `FAUCET_AMOUNT` (100), `FAUCET_COOLDOWN_HOURS` (24), `FAUCET_DAILY_CAP` (5000);
- релейер: `RELAY_PER_IP_HOUR` (10), `RELAY_DAILY_CAP` (500), `RELAY_MIN_FEE` (0, в LTH, только для V6);
- `RELAY_FAIL_PER_IP_HOUR` (20) — сколько отказов и неудачных запросов в час принимается с одного IP; `RELAY_MAX_QUEUE` (30) — сколько запросов может ждать очереди, остальные получают 503. Слот почасового и дневного лимита резервируется при получении запроса и возвращается, если запрос отклонён до отправки. Получатели-контракты релейером не принимаются (могли бы сжечь его газ).
- `RELAY_RATE_PER_MINUTE` (60) и `FAUCET_RATE_PER_MINUTE` (30) — ограничение частоты запросов к релейеру и крану на уровне Caddy, по IP.
- `FAUCET_EXEMPT_IPS` и `RELAY_EXEMPT_IPS` — список IP через запятую, для которых лимиты на IP и дневной лимит не действуют (для нагрузочного теста с самого сервера: `2.31.52.222,127.0.0.1`). После теста списки очистить.

## VPN для администрирования (WireGuard)

Публичные сервисы (RPC, обозреватель, кран, релейер, страницы) остаются открытыми. Закрывается только вход по SSH: после настройки он возможен только через туннель.

1. На ноутбуке установить WireGuard, создать пустой туннель («Add empty tunnel»), скопировать его **публичный** ключ (приватный остаётся на ноутбуке).
2. На сервере: `./vpn/wg-setup.sh ПУБЛИЧНЫЙ_КЛЮЧ laptop` — печатает блок `[Peer]` для туннеля на ноутбуке.
3. Включить туннель и проверить: `ssh -i C:\Users\smirn\.ssh\latheon_server root@10.66.0.1`.

## Нагрузочный тест и проверка анонимности

`./loadtest-cmd.sh` (по умолчанию пулы V7; `LOADTEST_GEN=v6` при `plan` — пулы V6). Шаги разных кошельков идут параллельно (`LOADTEST_CONCURRENCY`, по умолчанию 4), шаги одного кошелька — строго по очереди. Много кошельков в течение суток ведут себя как люди: кран, депозиты в пулы и через роутер, выводы на новые адреса целиком, частями и по нотам, через релейер и со своего кошелька, часть через мост из Arbitrum Sepolia. Все действия пишутся в закрытый журнал. Потом `analyze` играет наблюдателя, которому доступны только публичные данные сети, пытается связать выводы с депозитами и сверяет свои догадки с журналом.

```bash
./loadtest-cmd.sh plan --wallets 200 --bridge 25 --hours 24
./loadtest-cmd.sh fund        # LTH в сети, ETH и тестовый LTH в Arbitrum Sepolia для кошельков моста; ключ деплоера скрыто
./loadtest-cmd.sh start       # в фоне; ./loadtest-cmd.sh status | logs | stop
./loadtest-cmd.sh analyze     # loadtest/out/loadtest-report.md
./loadtest-cmd.sh hashes      # выводы через мост, которые можно забрать на странице моста
./loadtest-cmd.sh sweep       # после analyze: тестовые LTH с адресов получателей и кошельков теста обратно на главный кошелёк
```

`loadtest/secret/` (ключи кошельков, журнал) не публикуется. Отчёт ключей и адресов кошельков не содержит. Это симуляция: поведение задали мы, отчёт показывает, какие привычки выдают пользователя простым эвристикам, а не как ведут себя настоящие люди. Выводы через мост обратно в Arbitrum Sepolia тест только запускает; забрать их можно через страницу моста. Адреса получателей выводятся из главного ключа теста (он остаётся на сервере), поэтому `sweep` возвращает выведенные LTH; в прогоне V6 от 26–27 октября получатели были случайными, и выведенные там LTH вернуть нельзя. Новый прогон: старую папку `loadtest/secret` переименовать, `master.key` из неё можно скопировать в новую, чтобы использовать остаток на главном кошельке.

## Проверка старых пулов (до V7), только чтение

Все пулы до V7 (V3–V6, в том числе V5 в Ethereum Sepolia, Arbitrum Sepolia и Robinhood Chain Testnet) несут уязвимость схемы (THREAT-MODEL §8.0). В нашем интерфейсе они заморожены, но сами контракты по-прежнему принимают депозиты. `./legacy-pools-check.sh` для каждой сети из `deployments.json` читает у таких пулов баланс (монета сети или ERC-20), `nextIndex()` (сколько было депозитов) и число событий `Withdrawal`, а у старых роутеров баланс, и печатает таблицу. Ключи не нужны, транзакций нет: только `eth_getBalance`, `eth_call`, `eth_getLogs`, в одноразовом контейнере `node:22`.

```bash
./legacy-pools-check.sh                       # все сети; deployments.json из репозитория Latheon (main, demo/deployments.json)
./legacy-pools-check.sh --all                 # то же, плюс пулы V7 для сравнения
./legacy-pools-check.sh --network latheon-testnet
```

Сеть Latheon читается через локальный RPC узла (`127.0.0.1:8449`), остальные через публичные RPC из `deployments.json` (переопределяются `RPC_ETHEREUM_SEPOLIA`, `RPC_ARBITRUM_SEPOLIA`, `RPC_ROBINHOOD_TESTNET`). Флаги: `WITHDRAWALS>DEPOSITS` (выводов больше, чем депозитов) и `BALANCE<EXPECTED` (на пуле меньше, чем депозиты минус выводы) означают, что надо разбираться, и дают код выхода 1; `balance>expected` (монету или токены прислали напрямую) и `router-holds-funds` — для сведения. Полный результат: `legacy-pools/out/legacy-pools.json`. Проверка без сети: `node legacy-pools-check-test.js`.
